# 14 · 三端账号与数据同步方案

更新：2026-11-09。状态：部分独立核心已实现，完整三端云同步后置，实际模块见 [16](16-账号同步实现交接.md)。当前优先顺序见 [10 第 0 节](10-AI世界分阶段开发计划.md#0-当前发布路线)与 [12](12-开发交接与进度.md)，本页不作为自动开始下一项同步工作的指令。

## 0. 与当前桌面任务的区别

R03 的桌面窗由本机 DSH 插件启动，和同一 profile 的内嵌房间接续同一个家。需要补受限宿主桥、完整本地素材和单一可编辑视图的交接，不能等待整套云同步完成。具体边界见 10 第 0.4–0.5 节。

本页主要描述 Web、独立 App、DSH 和其他设备的账户级续用。已有身份、版本快照和同步队列保留，完整接入暂缓。房间布局保存、公开角色、模型能力和私人记忆仍分别处理；客户端登录不意味着 DSH 模型已经在线。

## 1. 用户应得到什么

同一用户在 Web、DSH 插件和 Electron 登录同一服务的同一账号，可以找到同一个角色、选择同步的房间、家具来源和共同经历。换端不会生成另一套同名角色，不会覆盖另一端未保存的布置，也不会让两个客户端同时控制同一个共享角色。

三端共享账号下的数据；模型能力随实际连接的设备提供。Web 用户可以无模型游玩。登录成功、房间已同步、私有记忆已迁移、AI 正在线是四种不同状态。

首轮依次解决“身份一致 → 房间和家具可续用 → 同场接管 → 共同经历可续用”。私有人设/感想的加密多端同步和跨设备调用模型安排在后续，不能以“全部数据同步”提前宣传。

## 2. 现有实现的真实边界

| 代码 | 当前作用 | 不能直接当成的能力 |
|---|---|---|
| `web/roomkit/app.js` 的 `localStore()` | 按前缀把场景和偏好写入 localStorage | 账户数据库、冲突合并、跨端同步 |
| `src/client.js` 的 `pullStore()/pushStore()` 与 `lib/index.js` | 启动读取 DSH 宿主存档，每两秒推送变动的 `dsh-room.*` 键 | 公共云同步；覆盖 IndexedDB 的完整备份；多个独立编辑端的冲突解决 |
| `packs.js` 的 `PackStore`、`world-drafts.js` | 家具包和世界草稿存在各端 IndexedDB | 已随 DSH 的 localStorage 镜像同步 |
| `desktop/main.js` | `app://roomkit` 下两个窗口共用本端存档；完整窗和小窗交替存在 | 与浏览器或 DSH 共用存档；远端账号同步 |
| `src/web.js` | 独立 Web/示例选择不同存档前缀 | 新浏览器自动知道旧设备的家 |
| `world-service.mjs` | 账号所属世界草稿与已发布版本 | 私人多房间家、家具收藏、角色私有设定的通用云存档 |
| `world-session.js` | 本地角色 ID 映射到服务端角色；映射保存在本端偏好 | 同一账号在空白设备上自动选回同一角色 |
| `world-sessions.mjs` | 场次权限、状态、事件、租约代次、显式接管 | 私人编辑冲突合并；任意跨设备模型代理 |
| `experience.js` | 按本地角色和服务保存经历、导入导出、补写感想 | 账号级永久经历库；导入记录已通过服务器真实性核验 |

当前 DSH 镜像注释中的“多端共享”仅指使用同一宿主存档的页面，不能解读为三款客户端的账户同步。当前 Electron 完整窗口没有与桌面小窗相同的 preload；增加账户桥时要分别接入并验证，不能只改小窗。

## 3. 总体组织

三端共用一层账户与数据接口，各自保留本地缓存和宿主适配器。平台提供账户存档、公开资源目录和 RoomHost，不为每个角色启动常驻模型进程。

```text
Web 场景       DSH 房间       Electron 小窗/完整窗
    │             │                   │
    └────── 共享账户与同步模块 ────────┘
                  │
       账户资源接口 + 素材存储 + 世界目录
                  │
          RoomHost 场次状态与控制租约

DSH 模型 / Electron 本机模型适配器 → 生成意图 → RoomHost 检查并提交
三端本地缓存 → 离线编辑可用；网络恢复后按版本提交
```

区分两条通道：房间、家具、角色资料使用低频存档同步；在线位置、互动和活动进度沿用场次事件同步。不要把场次快照写回私人房间，也不要通过同步整个场景 JSON 传播每帧动画。

## 4. 哪些数据同步

| 数据 | 第一阶段处理 | 同步依据与用户可见范围 |
|---|---|---|
| 账号、公开角色 ID、昵称、外观引用 | 三端共享 | 服务端账号归属；公开字段单独列白名单 |
| 私人家的房间列表、布局、房门连接 | 用户选择“保存到账户”后同步 | 账户私有资源，默认不公开；未选择的本地家继续离线保存 |
| 游客本地草稿、现有 DSH/Electron 存档 | 登录后可选择认领/导入 | 明确一次选择，不静默上传或覆盖已有云端家 |
| 家具收藏、固定版本和改编来源 | 同步清单，素材按需下载 | 固定发布者/作品/版本/摘要；缓存可重建，来源记录应保留 |
| 私有自制家具 | 与所选账户房间一同保存必要依赖 | 只有所有者可取；公开分享走独立发布审核 |
| 世界作品、已发布版本与可见性 | 复用服务端记录 | 私人草稿、固定版本、运行场次分开 |
| 共同活动事实和完成凭证 | SYNC05 增加账户级经历索引 | 以本服务核验的参与和完成记录为准，仅本人可见；公开游记另行发布 |
| 私有人设、聊天历史、角色感想 | 首轮留在主人端 | 后续可选加密同步；未迁移时明确提示，不把公开资料当完整记忆 |
| 模型密钥、DSH 凭据、登录令牌、控制租约 | 不进入同步内容 | 设备自己的凭据存储；各端分别登录，服务端可撤销 |
| 窗口位置/置顶/点击穿透、相机和临时 UI | 每端独立 | 适配设备，不把桌面设置同步到 Web |
| 动画、临时对白、精力等本地模拟数值 | 首轮不作为跨端权威养成值 | 未来定义明确的成长事件与结算规则，再加入同步 |

新建账户房间时界面明确标为“保存到账户，仅自己可见”；游客和历史本地房间必须先经过认领选择。私人房间同步是备份与跨端续用，发布为世界是另一项操作。账户私有访问控制不等于端到端加密，首轮不能宣称服务器看不到房间内容。

禁止序列化原始 `agents`/角色卡后整份上传：场景数据可能夹带人设、历史、宿主会话标识和模型配置。先建立房间布局、公开角色、素材清单等专用同步结构，并在客户端与服务端分别校验白名单。DSH 旧的前缀键扫描不得升级成上传整个 localStorage 的网络备份。

## 5. 身份、登录与跨端认领

### 5.1 稳定身份

继续使用服务端 `accountId` 和 `characterId`；新增账户的默认角色引用。`localCharacterId` 保留为历史设备映射键，不能单独承担跨端身份。不同服务中的身份以服务来源加 ID 区分，不能用昵称或邮箱自动合并。

登录顺序应为：确认服务与账号 → 拉取已有角色和默认角色 → 恢复/选择角色 → 加载账户资源 → 可选认领本地内容。当前 `Town.connect()` 会把本地主角同步给服务端角色，新流程必须避免“空白端默认角色覆盖已有昵称和外观”。

已有本地角色首次认领时，可选择关联自己已有角色或建立新角色；只显示该账号拥有的候选。关联不等于把另一人的角色迁到本账号。首次无内容的新账号可直接获得一个中性角色，后续再改外观和设定。

私人家使用独立 `homeId`，其房间使用家内稳定 ID；同步版本 `syncVersion` 与世界发布 `revision` 不混用。将某个房间发布为世界时生成固定内容快照，并保留来源关系；更新私人家不会直接改变已经运行的世界。

### 5.2 凭据与返回目标

复用现有 OAuth 与一次性登录领取流程，保留过期、取消、重复领取和账户失效检查。DSH/Electron 在系统浏览器完成授权，再把结果交给发起端；新引入的原生 OAuth 授权码流程应使用 PKCE。原生应用使用外部浏览器是 [RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252) 的推荐做法。

- 每端持有自己的可撤销登录会话；不用拷贝 Cookie、localStorage 或 DSH 登录凭据来实现跨端登录。
- Web 可将本站会话放在安全 Cookie/BFF 中；若迁移现有 Bearer 方式，必须同时处理 CSRF、登出、兼容及跨端客户端，不能只删请求头。未完成迁移前明确保留现有认证机制。
- DSH/Electron 的凭据存储走受限宿主适配；不向通用页面暴露完整令牌集合，不把登录令牌写进分享链接、日志、存档或素材包。
- 登录前保存的目标为经过校验的站内路由和邀请意图，登录返回后继续。禁止任意外站 `returnTo` 跳转，禁止把 OAuth 令牌当邀请或应用唤起参数。
- 换服务时旧服务会话不能发给新服务；地址校验只允许支持的 HTTP(S) 来源，生产入口用 HTTPS。接入自托管节点仍需独立信任与权限边界。

不要在账户切换后继续发旧账号的待同步队列。登出/换账号时停止 AI、取消在途任务、释放或失效控制权，清理当前视图中的私有数据；本地未上传内容按旧账户隔离保留，并能明确找回。

### 5.3 Electron 的特殊约束

保留 `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`。账户桥只暴露固定操作并验证发送窗口、来源和参数，不能暴露任意文件读写/任意 HTTP 代理。公共世界内容不能通过桥取得本机权限。遵守 [Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)。

Electron 完整窗需要独立的最小账户桥；窗口控制权限仍只给需要它的小窗。OAuth 链接交给系统浏览器；远程展示内容不共享本机高权限 preload。应用更新与家具包更新分别处理。

## 6. 存档同步与冲突

### 6.1 首轮采用有版本的资源快照

先以“一个家/一个可编辑资源”为提交单位，不做多人实时协同布置。服务端保存当前版本和有上限的历史；客户端保存已确认基线与未提交修改。大型图片单独按摘要存储，不在每次保存中重复上传。

拟议写入结构示意，不属于已实现的场次协议：

```json
{
  "format": "roomkit.account-resource",
  "schemaVersion": 1,
  "resourceId": "稳定资源ID",
  "kind": "home",
  "baseVersion": 3,
  "mutationId": "本次提交的唯一ID",
  "deviceId": "当前设备标识",
  "assetRefs": [{ "assetId": "家具作品ID", "version": "1.0.0", "hash": "内容摘要" }],
  "payload": { "经白名单筛选的布局字段": "..." }
}
```

账号由认证结果决定，`deviceId` 只用于展示来源和审计。服务端在事务内比较 `baseVersion`，匹配后才更新并递增版本；不匹配返回冲突和当前版本。同一 `mutationId`、同一内容重复发送返回同一结果；相同 ID 配不同内容拒绝。新建资源也应有创建幂等与不存在条件。

可以采用现有 POST 风格的应用版本字段，或 HTTP `If-Match`，但只选一套一致的冲突语义。条件更新用于避免丢失覆盖，参见 [RFC 9110 的 If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)。不能用客户端“最后修改时间更晚”直接覆盖另一端。

### 6.2 一次保存的顺序

1. 编辑立即落本地缓存和待提交记录，界面区分“本机已保存”与“账户已同步”。
2. 停止连续编辑后合并提交，允许短暂防抖；不每帧写云端。
3. 查询所需素材，先上传缺少且有权保存的依赖，校验摘要与额度。
4. 原子提交资源及引用；只有依赖齐全才能确认成功。暂存但未引用的上传按期限清理。
5. 服务器返回版本后更新基线，才清理对应待提交记录；失败保留重试。

切换房间/关闭窗口前尽力提交，但不能依赖关闭事件完成网络请求。本地持久化必须先完成，下一次启动能继续。

### 6.3 并发与离线

例：DSH 和 Web 都从第 3 版开始编辑。DSH 先提交成为第 4 版；Web 提交第 3 版基线时冲突。Web 保留自己的副本，提示“另一端也修改了这个家”，允许查看账户版或把本地改动另存为副本。首轮不自动合并家具坐标和房门关系，也不静默选任一端覆盖。

离线可以编辑本地家；恢复网络时先检查远端版本再提交。网络中断后的重试必须幂等。不要把离线期间积累的行走、发言、AI 意图在重新进场时批量补发；实时行为重新从当前状态决策。

首次升级只迁移副本，先保留可恢复的旧存档。localStorage、IndexedDB 的家具/草稿和本机经历分别迁移；使用迁移标记和 ID 映射避免重复导入。遇到缺失素材，标明缺失并保留布局，不假装房间已完整同步。

删除使用有版本的删除记录和恢复期。旧离线设备恢复后不得把已删除资源自动复活；超过增量游标保留期时先拉完整清单，未提交旧改动保留为本地恢复副本。资源回收必须考虑历史版本和仍被引用的素材。

## 7. 家具与场景的跨端一致性

同步家具的来源和固定版本，不仅同步包名。现有 `PackStore` 按包 ID 替换的行为需要迁移到能区分发布者、作品、版本/摘要的存储键，支持运行旧场次所需版本继续存在。

- 公共家具从可信目录取得对应版本，核验内容；本地文件导入保留“来源未核验”状态。
- 收藏清单与二进制缓存分开；清理缓存可以重新下载，不丢失收藏与改编链。
- 私人素材按账号授权读取；不能因为摘要猜中就允许其他账号下载。去重不能泄露私人素材是否存在。
- 公共审核状态保存在目录，不写死进不可变版本；下架后停止新分发/公开展示，通知已持有设备，离线副本不能保证即时召回。
- 家具定义、某个房间的家具实例、共享场次的实例状态分别记录。获取家具不会复制公共场次里的开关或活动进度。
- 在他人世界为显示所需而临时加载的素材，不自动加入自己的永久收藏；明确获取后再同步收藏。

格式、图片、占地和交互动作沿用严格校验；公开家具只允许受限数据，不能夹带任意代码、模型配置或系统指令。摘要证明内容一致，不能替代来源核验、内容审核和 AI 输入隔离。

## 8. 跨端进入世界与唯一控制权

共享场次继续由服务端 RoomHost 判定。沿用 `sessionId / epoch / seq / controlGeneration`，不另造一条“桌面同步”旁路。

用户在 DSH 带角色进入后，又用 Web 打开同一场次：

1. Web 识别为同账号同角色，展示当前状态，默认不抢控制权。
2. 显示“正在另一设备中活动”，用户选择“在这里继续”才接管。
3. 服务端提升控制代次；旧端停止自动 AI、取消请求，迟到的旧动作必须被服务器拒绝。
4. 新端取得快照后继续；只订阅或浏览不会生成第二只角色。
5. 已在其他场次时显示“返回原场”或“离开并前往”，复用当前每账号单一在线场次约束；不要为了 UI 方便并行加入多个场次。

私人房间中的展示动画可以各端自行运行，但首轮不把这些动画结算为全局养成收益。私人布置的写入冲突由资源版本处理；共享房间动作由控制租约处理，两者不能互相代替。

Electron 小窗与完整窗切换需保证同一个本地保存者。未来如果改成同时显示两个窗口，必须明确其中谁负责持久化/AI；同源共享 localStorage 并不能解决竞争。

## 9. 角色经历与 AI 的延续

### 9.1 共同事实先同步

账户经历索引以服务来源、场次、完成凭证和稳定角色身份去重。服务器核验本人参与及完成结果，再保存本人可恢复的经历记录；客户端导入的任意 JSON 不能凭结构合法就获得“已核验完成”标签。

当前完成凭证有保留期限，账户经历库必须在清理前完成可靠归档，或明确显示可补领期限。已经确认保存到账户的经历，不能在场次清理后消失。活动公共聊天不整段当私有记忆上传，其他玩家未公开的人设也不进入记录。

Web 没有模型时保存事实；用户回到 DSH 后可以为同一角色补写感想。事实记录与主观感想分别显示来源。云端第一次只恢复事实，不自动生成“我记得你所有过去”的表述。

### 9.2 私有记忆与模型后续实现

私有人设、聊天历史和主观感想首轮保持本地，可由用户明确导出/导入。要提供无感多端续用，后续再实现经过设计与验证的加密同步，包括设备加入/撤销、恢复方式、版本冲突和删除；不能只给请求套 HTTPS 就宣称端到端加密。

模型密钥保持在实际调用端。DSH 可使用已有默认模型；Electron 需新增明确的本机模型适配器，现有 `src/web.js` 对本机 HTTP 的网关检测不会自动适用于 `app://roomkit`。普通公网 Web 首版直接提供手动模式，不要求用户填写 API Key。

未来如让 Web 调用用户在线 DSH/Electron：必须建立用户可撤销的设备绑定和仅限世界决策的能力授权，限制来源、房间、额度及在线有效期；原设备离线立即降级。该能力不是文件同步，也不能实现为通用远程命令或让公网网页随意访问 localhost。首轮不承诺。

## 10. 接口与文件分工

拟议账户接口沿用既有路由风格；名称可在实现前与 UI 负责人统一，权限和行为不能省略。

| 接口组 | 主要职责 |
|---|---|
| `accountBootstrap` | 当前账号、已有/默认角色、资源概要、同步能力和设备信息；不返回其他端密钥 |
| `accountResourceList/Get/Put` | 私有家与清单分页、版本读取、条件写入、幂等与额度 |
| `accountResourceDelete/Restore` | 带版本的删除与恢复；传播删除记录 |
| `accountChanges` | 按账号的增量游标；过期时要求完整同步，分页且有上限 |
| `accountAssetCheck/Upload/Get` | 素材缺失检查、受限上传、私有读取和引用完整性 |
| `accountExperienceList/Claim` | 核验与归档本人经历，避免重复领取 |
| 设备会话管理 | 展示/撤销各端会话；不把 deviceId 当认证凭据 |

建议提取共享 `account-client`、`sync-store`、`sync-client`、`identity` 模块；文件名是设计建议，新增前检查已有实现。账户服务与迁移可放在独立 `scripts/account-*`，复用现有 SQLite 事务和身份检查。`town.js` 逐步拆出认证/传输接口，不要求一次重写旧社区。

关键复用与改造位置：

- `app.js/localStore()`、`home.js`：本地编辑缓存与稳定家/房间引用。
- `packs.js`、`world-drafts.js`：完整内容迁移、版本化素材和草稿，避免只迁移 localStorage。
- `town.js`、`world-session.js`：账户切换、角色映射、进入与接管流程。
- `experience.js`：事实与感想分离、稳定角色索引及旧记录迁移。
- `src/client.js`、`lib/index.js`：DSH 本地镜像兼容与受限宿主适配，不能直接公开原本机存档接口。
- `desktop/main.js`、`preload.cjs`：双窗口生命周期、凭据/账户桥、模型适配与退出保存。
- `world-store.mjs`、`town-store.mjs`：迁移/备份模式；新账户表不得破坏旧世界与旧账号。

## 11. 分阶段任务

UI04 的交互设计可以提前，真实家具分发和来源验证要有对应后端。UI06 随各阶段记录真实用户路径；SYNC06 与 W13 后续按需求继续。W11 月度流量仍留到完整路径可用后收尾。

## 12. 必须验证的场景

1. 新用户在 Web 登录、修改账户房间；DSH 和 Electron 登录同账号后取得相同布局、门连接、家具版本与角色身份。
2. 有历史本地家和已有云端家时，迁移保留双方内容；重复迁移不生成多份角色/家具；未选择同步的私有内容不上传。
3. A、B 两个账号轮流使用同一浏览器/客户端，不泄漏房间、经历、凭据或待提交修改；退出后旧 AI 请求不能发言。
4. 两端从同一版本编辑，冲突时双方修改都可恢复；离线、刷新、请求超时重发不重复创建资源。
5. 图片已上传而存档提交失败、依赖缺失、额度用尽和存储不可用时，状态真实且内容可找回。
6. 删除传播后旧端重连不会复活记录；恢复期和历史清理按约定工作。
7. 同账号两端进同场不会出现两个角色；显式接管后旧端控制失效，包括正在返回的模型动作。
8. Web 无模型仍可完成活动；DSH 补写感想不修改完成事实；伪造导入经历不能获得已核验标记。
9. 私有素材、账户接口、经历均进行服务器授权检查；同步内容不包含模型密钥、登录令牌或未选择的私有人设。
10. 旧客户端遇到不支持的新格式保留本地数据并解释升级要求，不覆盖新格式；升级、回滚、备份恢复有真实验证。

每阶段只运行相关检查。完成一项后记录支持哪些端、哪些数据、哪些失效场景，不能把“能登录同一账号”或“导入一次文件”标为三端同步完成。
