# 09 · AI 世界方向与产品边界

更新：2026-11-09。本文记录 pigeon 已确认的产品方向。[分阶段开发计划](10-AI世界分阶段开发计划.md)规定实施顺序，[首版契约](11-AI世界首版契约.md)记录已实现的共享场次边界，[开发交接](12-开发交接与进度.md)供接续执行。13、14 保留 UI 与同步设计，领取顺序以 10、12 的最新安排为准。

## 0. 当前优先交付

先让用户从视频或 GitHub 项目页打开网页看到效果，再通过公开可获取的 DSH 插件进入自己的房间、使用宿主模型互动，并在插件内选择“放到桌面”。插件负责准备运行环境和启动透明辅助窗口，用户不必手动再装一个 App。独立 Electron 下载包作为后续渠道。有创作兴趣的用户可以布置、导出房间，再登录发布固定版本并邀请别人来访。以少量真实用户的首次体验和反馈决定下一轮。

公共世界持续扩建仍是长期方向，不作为本轮发布前置。完整三端同步、公共家具市场、多区域连接、用户托管和复杂玩法暂缓。保留已经完成的模块，按这条体验路线接入必要部分。同一 DSH profile 的内嵌房间和桌面辅助窗必须接续同一份家，先采用单一可编辑视图与可靠存档交接。Web、独立 App 和其他设备初期可以分别保存本地数据；界面和宣传必须说明存档位置，不能将同账号登录描述为完整同步或自动接通 DSH 的 AI。

GitHub 公开仓库用于一起做房间、家具和玩法，Issues 收集安装和使用反馈，在线试玩和安装下载继续复用公网试玩站。演示保留 Q 版鲸鱼娘，玩家可以换成自己的角色。引擎包、DSH 插件和独立 Electron 应用各自交付，插件可以自行管理桌面辅助进程。DSH 房间调用宿主模型，不等于已导入其他宠物插件的身份和私有记忆。桌面辅助窗运行在 DSH 宿主所在电脑，远程服务器上的 DSH 不能直接在访问者桌面开窗。 [共建仓库](https://github.com/HarrisonDo/dsh-room) · [Issues](https://github.com/HarrisonDo/dsh-room/issues)

## 1. 我们要做什么

RoomKit 要成为连接用户、用户培养的 AI 角色和用户自建世界的桥梁。用户可以布置自己的 2.5D 世界，邀请朋友带着各自的 AI 来访，也可以一起进入其他创作者提供的交流空间或探险副本。活动中的共同经历能够带回各自的角色，影响以后的交流。

世界的内容和生命力主要来自用户。长期提供一个逻辑上相连的公共世界，从公园起步，接纳用户提交的标准场景版本，通过道路或门连接区域；区域还可保留通往开放或受邀私人场景的入口。实际运行可以按区域加载和暂停。平台提供共同格式、连接方式、发现入口和必要的公共服务，不负责让所有离线 AI 永久运行。

大肥鱼是项目的起点和一种角色内容。引擎、世界格式和连接能力应允许独立的角色形象、模型服务和宿主接入。实现上的独立与许可上的独立需要分别完成，不能只改名称就宣称已完成拆分。

## 2. 已确认的产品原则

1. **用户有自己的世界和 AI。** 私人世界可以只保存在本机；模型可由用户自己的服务提供，不要求在用户电脑上运行大模型推理。平台不集中代养全部 AI。
2. **先做好本地陪伴，再增加小型共同活动。** 首发先解决安装、互动、桌面陪伴和创作；A、B、C 的互访及 D 的活动场景复用已有联机能力逐步打磨。
3. **公共空间是交流入口。** 公共广场、主题活动、玩家开放的副本都可以存在，规模和开放时间由实际需求决定。
4. **世界有共同语言。** 同一物件有哪些动作、动作是否成功、活动是否完成，要有统一的结构化含义；不能只共享一张画面。
5. **经历属于参与者。** 共同事实在一场活动内一致，角色对它的印象、人设和私人记忆由各自主人保管。
6. **内容可以共同改进。** 用户分享、复制或提出改进版本，作者选择发布；正在游玩的场次继续使用开始时的版本。
7. **资源随使用增长。** 无人使用的房间暂停运行，AI 调用按用户选择和预算发生，不为每个注册角色启动永久后台进程。
8. **先体验，再按需接入。** 公网试玩站打开即可体验和布置，注册/登录后逛开放场景或进入朋友房间；DSH、Electron、模型配置都不是 Web 入场前置。账户下选择的内容以后可跨端同步，宿主能力各自提供，不作为首发依赖。

## 3. 三个问题要分开

“谁创作世界”“谁可以进入”“谁运行这场活动”是三件事。公开作品可以由玩家托管，私密活动也可以临时使用平台服务器。

| 形态 | 内容由谁提供 | 谁可以进入 | 运行安排 |
|---|---|---|---|
| 私人小屋 | 用户 | 用户自己 | 本机运行；可保留本地，也可选择账户私有存档跨端续用 |
| 邀请串门 | 用户 | 受邀成员 | 首版使用轻量服务同步，后续支持房主托管 |
| D 的探险副本 | D 发布模板 | 按 D 的规则组队 | 每个队伍建立独立场次，用完暂停或结束 |
| 公共交流空间 | 平台或玩家 | 符合开放条件的成员 | 平台或自托管节点按需运行 |
| 世界作品目录 | 所有创作者 | 按作品可见性展示 | 平台主要保存介绍、版本、入口和可公开的访问记录 |

用户提供内容会减少内容制作压力；只有实际把运行和模型调用分散出去，才会减少对应的服务器开销。账号、连接转发、共享素材、存储、审核和备份仍然需要资源。

## 4. 论坛在其中的位置

这里的论坛是内容组织比喻：一个分享场景对应一份作品档案，包含作者、版本、来源、玩法和可公开的访问或活动状态。文字视图帮助发现和回顾场景，不将普通发帖、自由回复作为新产品主流程。

长期结构为：**场景作品 → 固定发布版本 → 公共区域或独立场次 → 参与与活动 → 经历与作品档案**。作品、公共连接和运行场次各有身份，不能用帖子 id 代替全部对象。公共位置分配、区域撤下与版本更新的具体方案留到连接阶段。

现有小镇数据继续保留，但“旧社区”不再作为产品宣传或主导航概念。目标中的用户公开表达以八种情绪为基础，自由文本聊天不属于目标公共交互；协作动作和 AI 公开表达的具体规则尚待小规模验证。当前协议仍支持 say，不能仅隐藏输入框就宣称限制已经实施。

## 5. 已完成的首条联机技术闭环

以下是 W00–W10 的历史实现目标，用“合作点亮庭院”验证共同状态。它用于复用和回归，不代表当前需要重复开发或将其中的聊天设计作为新方向。

1. D 使用已有布置工具建一个庭院，选择活动预设，指定三盏信标和出口，保存为自己的世界。
2. D 发布一个固定版本并开场，设置仅受邀成员进入，发出邀请链接或邀请码。
3. A、B 各自选择本地角色和模型接入方式。每个人看到将共享的公开资料；私人设定、历史和模型密钥不随入场上传。
4. 两人进入同一场次，看到相同的信标状态和成员列表。各自只驱动自己的 AI；房间内可以聊天、移动和互动。
5. 至少两个不同账号的角色共同点亮三盏信标，再打开出口。规则由本场的运行端判定，所有人收到同一份完成结果。
6. A、B 各自保存事实记录和角色视角的感想。下一次相遇时，角色能够召回“和谁、在哪个世界、一起完成了什么”。
7. 大家离开后回到原来的家。场次无人时暂停，不再触发 AI 对话或持续模拟；世界作品仍可再次开场。

活动完成与聊天模型成功无关。无模型、超时或额度耗尽时，用户仍可手动操作；模型恢复后可以补写感想。不能因没有一句模型摘要就丢失这次经历。

## 6. 首版实施取舍

这些是 W00–W10 首条闭环采用的工程默认值，作为历史实现边界保留。该闭环已完成，最新状态见 12；当前优先顺序为 10 第 0 节的安装与桌面路线，13、14 的完整家具和云同步方案后置。

| 首版实现 | 后续再做 |
|---|---|
| 一次发布一个场景，现有多房间的家继续本地使用 | 一个联网世界包含多区域并跨区运行 |
| 每场默认最多 4 个账号，每账号带 1 个角色 | 多 AI 编队、大型活动与观众模式 |
| 平台运行一个轻量场次判定器；客户端绘画，各自主人的接入端调用模型 | 房主电脑或独立节点托管，平台负责发现与必要的中继 |
| 现有 POST + SSE，按场次订阅 | 经测量确有需要后再换传输方式 |
| 一个有限规则的合作活动预设 | 通用任务编辑器、复杂剧情分支和开放脚本 |
| 本机经历记录、导出导入、下次召回 | 多设备加密同步、长期能力成长体系 |
| 先保留熟悉的房间 UI，增加建世界、邀请、活动和经历入口 | 整站视觉改版、交易、排行榜和庞大内容市场 |

首版把判定器放在现有服务端，是为了先解决权限、共同事实和断线恢复。它不运行渲染，不托管模型，也不持续模拟空房。判定逻辑与网络适配分开，后续才能迁到用户托管端，而不重写世界内容和客户端。

## 7. 2.5D 的作用

2.5D 继续作为主要表现形式：沿用等距网格、家具交互位、程序绘制与透明贴图，降低素材制作和展示门槛。重要的是固定尺寸、锚点、占地、遮挡、动作和可交互信息，使不同作者的内容能放在一起。

2.5D 本身不会降低模型调用费用。资源控制主要依赖用户自带模型、事件触发而非逐帧询问模型、小房间订阅、素材缓存和无人暂停。首版不追求所有动画逐帧一致，但共享物件、成员位置的逻辑结果和活动进度必须一致。

## 8. 服务资源边界

当前资源：用户提供的 Oracle 美区 8 核 24 GB 服务器，与个人服务共用 IP；带宽“50”暂按 50 Mbps 规划，月流量按用户提供的 500 GB 计算。这些是部署约束，不是并发容量证明。

- 游客与历史私人世界默认不上传；用户可选择“保存到账户”用于私有备份和三端续用，或另行“发布为世界”共享必要的场景、素材与规则。这两种操作权限和含义不同，前者不自动公开。
- 账户存档只含选择的布局、公开角色资料和必要素材引用；私有人设、聊天和模型密钥不随场景整包上传。增量存档、素材去重与缓存均设配额，不把私人离线动画变成服务器永久模拟。
- 世界列表只取元信息，不把全场景和素材混进每次列表广播。
- 场次事件只送给有权限且正在订阅的成员；不同房间之间不互相广播。
- 场次和连接有上限、超时、暂停与清理机制。模型并发、自动交流次数和重试也有上限。
- 正式宣传前要完成故障回归、受控负载测试、流量观测、备份恢复和同 IP 服务暴露检查。应用限流不能代替网络入口防护。
- 容量由活跃场次、连接数、消息频率、素材大小和实际带宽共同决定，不承诺“8 核能支持多少万人”。

## 9. 开源和素材边界

产品意图：开放场景引擎、格式、示例和必要的接入能力，让别人能创作和改进自己的世界；运营站点和论坛服务暂不把开源作为首版功能要求。

实施约束：当前仓库根许可证和包元信息声明 AGPL，部分旧文档和源码注释又写 MIT，默认构建还包含 Coopanion 相关内容。**新的产品方向不构成重新授权，也不表示现有服务端已经可以闭源。** 发布前单独完成来源、贡献权利、依赖、素材和构建产物审计，再决定仓库与许可证拆分。

首先做到引擎可在不加载大肥鱼相关模型和素材的情况下运行，角色提示词不写死物种，示例使用权利清楚的内容。技术拆分不自动改变第三方内容原有的许可条件。具体工作列入开发计划的 L1。

## 10. 成功标准

近期成功的标志是：新用户沿 GitHub/视频入口完成网页体验和 DSH 安装，无需开发环境即可互动并把同一个家放到桌面；创作者能导出可完整恢复的房间，后续登录分享给另一位用户。记录真实步骤、失败点、再次使用意愿与维护耗时，不以新增功能数量代替产品验证。

已有联机闭环继续用于验证同一次活动的共同结果与经历保存。公共世界扩建的下一次实验应是“一块玩家区域被接入并有人愿意再来”，通过后再增加区域、家具分发和自动同步。

“去中心化”“AI 宇宙”“养成”不作为功能已完成的宣传结论。首版实际支持到哪一层，就展示哪一层。后续开发依据这条流程的真实使用反馈推进。

## 11. 初期运营原则

- 本地体验和创作无需注册。联网来访、发布与公共推荐分开授权，登录不自动获得无限发布或公共编辑权限。
- 先用固定版本、受限素材、自动格式检查与维护者公开收录控制工作量。普通用户可以低门槛体验，公开分发能力按实际审核能力开放。
- 场景来源和摘要帮助追溯，不能证明无害。作者描述和场景文本不得成为 AI 的系统指令或工具授权，私人记忆和模型凭据不随场景传播。
- 八种情绪负责表达；明确的接受、拒绝和退出负责权限。主人与 AI 的私人交流、公开情绪和给作者/维护者的问题反馈分开设计。
- 公共区域数量依据活跃用户和维护能力增加，避免面积增长却找不到人。2.5D 与用户提供内容不会自动免除公共素材、存储、网络和审核成本。
- 优先测量是否能独立安装、是否愿意再次使用、是否能完成第一份作品，以及一份投稿需要维护者花多久。详细执行范围与发布门槛见 10 第 0 节。
