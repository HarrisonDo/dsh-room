## 4. 每轮工作规则

1. 检查实际代码和工作区变更；上一轮记录是入口，不能盲目信任已经变化的接口。
2. 说清当前任务范围。读取指定入口和对应测试，不把所有历史讨论重新塞入上下文。
3. 对照 11 实现最小可用结果。通用规则应复用；不要为让测试通过新增与正式路径无关的第二套模拟实现。
4. 只新增能验证风险与行为的测试。覆盖权限、状态一致性、重复提交、恢复和数据迁移；不写机械复刻实现的测试。
5. 完成相关检查后更新任务状态及下一节。没有新变更或失败原因，不反复跑相同全量检查。
6. 汇报实际结果；需要真实环境的步骤写具体，不把所有工作都笼统交回用户。

若获得多 agent 并行开发指令，先按模块指定文件责任范围。`app.js`、`shell.js`、`town.mjs`、`town-store.mjs`、构建入口和本交接页均由一个负责者修改；主 agent 汇总、去重、裁决冲突后合并。没有明确并行安排时顺序开发，避免共享文件冲突。

### W00 确定的模块文件与接口

下表路径相对 `dsh-room/`，实现按各自任务接入。

| 文件 | 接口职责 |
|---|---|
| `shared/world-format.js` | 发布输入 → 归一化的世界和素材依赖、摘要，或带字段路径的校验错误。复用现有场景和包格式。 |
| `shared/session-core.js` | 场次状态和命令 → 待提交事件或拒绝。状态与已提交事件 → 新状态。 |
| `shared/activities.js` | 场景及活动配置 → 物件与路径校验。活动状态和交互 → 规则结果，供场次核心调用。 |
| `scripts/world-store.mjs` | 通过 `createWorldStore({ db, q, tx })` 接入共享 SQLite，负责世界迁移和持久化。 |
| `scripts/world-service.mjs` | 接收传输层认证的账号与请求，处理权限、邀请、控制租约、RoomHost 生命周期及提交后分发。 |
| `web/roomkit/world-session.js` | 客户端提交意图，消费快照和已提交事件，处理补发、临时素材及离场恢复。 |
| `web/roomkit/agent-adapter.js` | 主人侧适配器提供 `describeCapabilities()`、`decide()`、`summarize()` 和 `cancel()`，通过观察生成意图。 |
| `scripts/local-agent.mjs` | 在本机预览的同源网关调用用户配置的模型服务，凭据留在本机。 |
| `web/roomkit/experience.js` | 从已提交事实和凭证写入本机经历，按角色去重，感想异步补写并兼容旧记忆。 |

W03 在 `town-store.mjs` 的 `openStore()` 初始化旧表后，将同一连接 `db`、语句缓存 `q` 和同步事务入口 `tx` 传给 `createWorldStore()`，通过 `store.world` 交给服务层。`openStore()` 负责连接、备份与关闭。新迁移在事务内写入 `world_schema_migrations`，场次用 `world_sessions` 区分登录会话。命令回执、事件、快照和完成凭证由服务层使用同一个同步事务写入，提交后再广播。

共享模块接入时，浏览器入口由 `scripts/build.mjs` 打包。分发检查包括 `package.json` 的 `files` 与小镇 Dockerfile 的显式复制列表。
