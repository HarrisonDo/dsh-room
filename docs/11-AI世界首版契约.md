# 11 · AI 世界首版契约

更新：2026-11-07。状态：**待实现的 v0.1 开发基线**，不是现有接口说明。产品边界见 [09](09-AI世界方向与产品边界.md)，任务依赖见 [10](10-AI世界分阶段开发计划.md)。只在实现发现具体冲突时修改对应约定并留下原因，不在每个任务里重新设计整套架构。

## 1. 名称与模块边界

| 名称 | 含义 | 与现有代码的区别 |
|---|---|---|
| WorldDefinition | 用户拥有的世界作品，含草稿和发布版本 | 不是 `scene.js` 中现有的 `World` 类；后者仍是场景编辑模型 |
| WorldRelease | 固定场景、活动规则和素材依赖的一次发布 | 发布后不可原地修改，编辑产生下一版本 |
| WorldSession | 一个队伍正在使用的场次 | 不等于登录会话，也不等于帖子 |
| Participant | 账号在本场选择的一个角色 | 账号身份由认证推导，不接受请求体自行声明所有者 |
| RoomHost | 本场共享事实的唯一判定端 | 首版在平台服务进程内，未来可由房主或独立节点运行 |
| AgentAdapter | 主人一侧调用模型或已有 AI 的适配器 | 不把模型凭据、完整人设和私人记忆交给 RoomHost |
| Experience | 一个角色对本次活动的本机经历记录 | 共同事实和主观感想分开存储 |

`shared/` 中的校验、状态归约和活动规则不依赖 DOM、DSH、HTTP 或数据库。RoomHost 通过外部传入的存储与消息发送能力工作。`WorldSession` 用 `world_sessions` 等命名，避免与现有登录表 `sessions` 冲突。

## 2. 世界发布格式

外层新增 `roomkit.world` v1，继续使用现有 `roomkit.scene` 和 `roomkit.pack`。现有场景会归一化到 v2；`docs/04` 的 v1 示例不作为新联网发布的版本号。

以下是字段形状，省略的场景与包内容按现有格式填入；不是可直接导入的示例文件。

```text
WorldRelease {
  format: "roomkit.world", v: 1,
  worldId, revision, title, authorAccountId,
  protocol: "roomkit.session/1",
  scene: <一个合法的 roomkit.scene，不含访客和私人角色资料>,
  dependencies: [{ id, version, hash, source: "builtin" | "embedded" }],
  packs: [<经过校验的内嵌 roomkit.pack>],
  activity: { kind: "cooperative-beacons", v: 1,
              beaconIds: [<三个物件实例 id>], exitId, minContributors: 2 },
  hash
}
```

- `worldId`、作者和发布版本由服务端绑定；本地草稿另有本地 id，不允许覆盖别人的作品。
- 活动可以为空，表示自由交流房；首个完整验收使用信标活动。`beaconIds` 和 `exitId` 引用本版本中真实存在的物件，不按显示名匹配。
- 发布校验必须返回明确的字段错误，不能靠 `normalizeScene()` 的容错能力充当安全校验。对结构、数量、字符串、数值、嵌套深度、图片字节和像素尺寸设置上限。
- 新发布包默认总请求体不超过 **4 MiB**；图片仍满足内容包已有上限，同时受这条更小的联网总额限制。这是可配置的首版限制，不修改本地导入原有 15 MB 内容包总额。
- 仅发布接口使用独立的上传额度和体积上限；普通命令保留小请求限制。不能为传素材把所有 API 的 400 KiB 上限统一放大。
- 内嵌包应带作者和许可信息。素材先沿用 PNG/WebP 的数据格式，不执行 HTML、脚本或随意获取第三方 URL。
- 服务端对归一化后的白名单内容计算稳定摘要。规范化规则固定键排序、数组顺序和字符串编码，摘要不包含 `hash` 本身。客户端同样校验，不依赖浏览器里已有一个同名包。
- 固定版本的内置包也要有版本和摘要；外链默认素材在构建时生成清单，服务端不抓取用户指定地址。无法解析的依赖拒绝发布或入场。
- 每场使用独立目录视图，避免临时包覆盖用户自己的家具库；离开时撤销临时安装的场次资源，允许有界缓存保留已验证的字节。
- 发布后改草稿不会改变已经开场的世界。新场次选择新版本，旧场次继续使用原版本。

## 3. 身份与邀请

首版每场最多 4 个账号，每账号 1 个角色。角色卡的 `id` 只表示内容，不足以作为跨设备或跨账号的身份。

- 主人本机保存稳定的 `localCharacterId`，并维护它与平台账号下 `characterId` 的映射；改名、换外形、重复导入同名卡片不能意外合并私人记忆。
- 入场只提交公开角色资料引用；公开外形缺失时使用中性后备形象。人设、模型连接配置和私人记忆不写入世界发布包或成员列表。
- 所有读取、邀请兑换、加入、快照、事件补发、素材获取和动作写入都校验权限。隐藏入口不是权限控制。
- 默认场次为 `invite`，仅创建者和兑换成功的成员可见。首版邀请绑定一个场次，不自动授予其他场次或世界编辑权限。
- 邀请使用安全随机令牌，服务端只保存摘要，默认 24 小时过期、最多兑换 1 个账号，可撤销。房主为多位访客分别创建邀请。
- 邀请链接把秘密放在片段中；客户端读取后清理地址栏，通过已登录的 POST 兑换。也允许粘贴邀请码，兼容 DSH 和本地预览入口。
- 兑换成功产生持久成员资格；同一账号重试返回原结果，不重复消耗次数。撤销未兑换邀请与移除已入场成员是两个操作。
- 房主可以请离成员并撤销其本场权限。撤销后立即断开该场订阅，拒绝后续读取与动作；已经看到或导出的内容无法收回。
- 本地开发身份只用于测试。公网模式必须使用真实登录并关闭 legacy / dev 入口。

公共目录和无需邀请的公开场次留到 W12，不默认把首版场次、成员、聊天或经历公开到论坛。

## 4. 场次生命周期和控制权

```text
创建 → active → paused → active
          └────────────→ ended
```

创建在事务内写好版本引用、创建者成员资格和初始快照。`paused` 保留进度，`ended` 不再接受游玩动作；重开同一作品建立新场次。活动完成是活动状态，不强制立刻结束场次，玩家可以继续交流。

- `worldId + revision` 决定内容；`sessionId` 区分各队伍；`epoch` 区分运行权代次；`seq` 是本场递增事件序号。
- 首版 RoomHost 在平台服务端：房主离开但仍有成员在线时可以继续；全员离线 60 秒后保存并暂停。无人时不跑逐帧模拟或主动聊天。
- 服务重启将未结束场次恢复为暂停，提升 `epoch`；有权限成员请求恢复后使用已提交快照和进度。旧代次请求返回需重新同步，不能继续写入。
- 同一角色仅一个客户端持有本场控制租约。第二窗口可看状态，接管必须显式发生；接管增加租约代次，使旧窗口的在途动作失效。
- 断线宽限期间保留席位，超时释放在线名额和控制租约；不抹去已经获得的经历。心跳、租约、在线名额都要有界清理。
- 后续房主托管时，房主失联即暂停，首轮不自动转移到访客；正式切换 Host 必须提升 `epoch` 并验证快照，不能同时出现两个判定端。

## 5. 命令和结果

首版命令形状：

```text
{ protocol: "roomkit.session/1", sessionId, epoch,
  requestId, actorCharacterId, controlGeneration,
  op: "move" | "interact" | "say" | "emote", args }

成功：{ requestId, status: "committed", seq, events: [...] }
失败：{ requestId, status: "rejected", code, message, latestSeq }
事件：{ sessionId, epoch, seq, type, actorCharacterId, payload, at }
```

认证信息由传输层传入。RoomHost 校验账号、成员权限、角色归属、控制租约、场次代次、白名单参数和活动条件，然后串行处理本场命令。

- `move`：目标坐标在合法地面且路径可达。首版采用离散逻辑落点，提交后客户端用动画表现路程；走路动画不决定机关时序，也不声称是实时物理模拟。
- `interact`：物件存在、角色逻辑位置满足交互位距离、活动允许这个动作。只执行预设允许的效果；不开放任意 `object.state`、`scene.load`、`story.run` 或脚本命令。
- `say`：沿用文本审核和额度，分清用户代说与 AI 自动产生的通道来源；来源标签不是“这段内容必定由真人书写”的证明。
- `emote`：白名单表现动作，不修改活动状态。
- 角色移动、聊天标记和 UI 点击都走这个命令入口。收到提交事件后才应用共享效果；不能由 `app.chat()` 先在本地执行，随后又执行服务端广播。
- 共享模式的远端角色关闭本地 `Brain` 自主决策和 `Director` 随机演出；本人的自主决策也只能生成待提交意图。客户端动画不能写回共享事实。
- `requestId` 在账号、场次内去重；同一个 id 携带不同内容要拒绝。已提交结果与事件、快照在同一事务中保存，重试不得再点灯或再次完成活动。
- 新生成的世界、场次、邀请和请求身份使用安全随机标识。返回历史回执前仍检查当前访问权限；异步审核完成后重新检查权限和配额，再进入短事务提交。
- `seq` 单调递增。客户端忽略已应用事件，发现缺口拉取补发；超出保留窗口时获取快照，不能带着缺失状态继续提交活动动作。
- 操作提交使用当前权威状态重新判断，不因为普通聊天产生了新 `seq` 就让所有动作冲突。`epoch` 和控制代次不匹配必须拒绝。
- 错误至少区分 `unauthorized`、`forbidden`、`expired_invite`、`room_full`、`unsupported_version`、`missing_asset`、`invalid_action`、`too_far`、`already_done`、`stale_epoch`、`control_lost`、`rate_limited`、`resync_required`。

## 6. 传输与存储

继续使用 POST 上行和 SSE 下行，先实现新世界接口，不强迫旧小镇协议一起改名。建议在现有 `/api/{name}` 路由风格下新增：

| 操作组 | 建议接口名 | 主要权限 |
|---|---|---|
| 世界 | `worldSave`、`worldPublish`、`worldGet`、`worldList` | 本人草稿；发布内容按开放范围读取 |
| 开场与邀请 | `worldOpen`、`inviteCreate`、`inviteRevoke`、`inviteRedeem` | 创建者管理，登录后兑换 |
| 场次 | `worldJoin`、`worldLeave`、`worldResume`、`worldEnd`、`worldKick` | 成员进入；创建者结束或移除 |
| 状态与动作 | `worldSnapshot`、`worldCommand`、`worldReplay` | 本场成员；写操作另验控制权 |
| 连接 | `worldStreamTicket` | 已验证的本场订阅身份 |

新 SSE 连接携带短期、限本场、一次性使用的票据，不把长期登录令牌放入 URL。断线重连重新领取票据并携带最后序号；长期连接也要处理登录过期、登出、封禁和成员撤销。旧小镇 SSE 的身份失效处理一起在 W01 修复。

建议新增世界作品、发布版本、场次、成员、邀请、命令回执、事件和完成凭证的存储；可在一个数据库中实现，不引入 Redis 或消息队列。迁移有版本号和事务，不复用旧的“任何 ALTER 失败都忽略”来掩盖错误。

广播按订阅场次和权限筛选；慢连接超过有界缓冲后断开，重连获取补发或快照。列表按页查询，不解析全部场景；聊天审核中的内容不能通过快照或事件回放绕过可见性检查。

房间 `seq` 只为所有有权成员共同可见的已提交事件编号。待审文本留在单独的作者通知通道，审核通过后才产生房间发言事件；移除内容发布相应删除事件。这样客户端不会因私有通知造成假缺口，也不会在补发时收到未获准的文本。

默认容量和保留策略必须集中配置并可观测：每场 4 人、每账号 1 个活跃场次、空场 60 秒暂停；暂存的空场/暂停场次 7 天后结束；事件与命令回执有条数和期限上限。完成凭证至少保留 30 天供断线用户领取，界面说明领取期限。具体事件窗口在 W04 实测后填入配置和文档，不把默认额度当成压力测试结论。

事件窗口回收依赖持久快照。命令回执回收不能让旧命令重新执行：首版可以在达到窗口上限时原子保存快照并提升 `epoch`，旧请求只得到重新同步错误，不能当成新请求处理。完成资格和凭证另存，不随短期事件窗口一起删除。

## 7. 首个活动规则

`cooperative-beacons` 只是一种有界预设，不是通用脚本系统。

1. 发布时验证恰好三个不同信标、一个出口、可用出生点和交互路径。首版不允许开场后共同编辑布局。
2. 第一次成功使用信标记下贡献角色及其账号，再次使用返回已经点亮。两个用户同时点同一盏，最多一个成功产生效果。
3. 三盏全部点亮，且贡献者来自至少两个账号后，出口可开启。用同一账号换两只角色不满足条件。
4. 合法开启出口产生唯一 `activity.completed` 事件和完成凭证；将当时在线且有资格的参与角色、贡献者、世界版本与完成序号一起固化。
5. 以完成瞬间的参与名单确定领取资格。已中途离开的成员保留自己的部分经历；完成之后才加入的角色不补发完成经历。资格判定与完成事件在同一事务内进行。
6. 完成后重复交互、网络重试、刷新、补发事件，都不得再次发放完成记录。

活动 UI 展示目标、进度、可尝试的动作和失败原因。AI 得到结构化的物件 id、位置、交互名、前置条件和最新结果，才能理解自己参与的是同一件事。

## 8. AI 适配器

接口职责：`describeCapabilities()`、`decide(observation, context)`、`summarize(facts, context)`、`cancel()`。名称可在实现时调整，边界不变：观察进来，文本或动作意图出去，不直接改场景。

- `observation` 来自本场已提交快照：角色、物件实例 id、允许动作、活动进度、近期事实与失败原因；不只有家具名称。
- `context` 在主人一侧装配人设、相关私人记忆和调用预算。共享场景与他人文本都是数据，不能增加工具权限。
- 首版提供：已有 DSH 模型适配、独立本地预览的模型网关适配、离线手动模式，以及测试用确定性适配器。
- 独立网关由用户在本机启动，网页和网关同源，通过用户配置的模型服务调用。密钥留在本机环境或受控配置中，不进入场景、邀请、日志、导出包或平台服务器。
- 本地网关只监听回环地址，校验 Host、Origin、请求身份及调用额度，不提供任意目标 URL 转发。公网网页首版可以展示作品和邀请说明；独立 AI 游玩允许粘贴邀请码到本地预览，不承诺公网 HTTPS 页面可直接调用任意本地端口。
- 自动行动默认需要主人开启；一次一个模型请求，设置超时、取消、每小时额度与失败退避。离场、断线、被移除或控制权丢失立即取消，迟到结果不得提交到新场次。
- UI 清楚显示“已接模型 / 手动模式 / 调用失败”。测试适配器和离线台词不能冒充真实模型验收。

## 9. 经历与记忆

```text
Experience {
  v: 1, id, localCharacterId,
  source: { serviceId, worldId, revision, sessionId, completionSeq? },
  participants: [<角色 id、当时名字>],
  facts: [<有来源事件的共同事实>],
  outcome: "completed" | "partial",
  reflection: { text, status: "pending" | "ready" | "fallback" },
  createdAt, updatedAt
}
```

- `serviceId` 首版使用规范化服务来源；永久角色 id 用于辨认身份，显示名只是标签。本机角色 id 不随服务地址变化丢失，跨服务身份合并暂不做。
- 完成经历使用稳定凭证 id，在本机按角色去重写入。部分经历以本次访问 id 保存，与完成经历可关联，不能把同一次活动算成多次完成。
- 一旦收到关键事实就写本机待处理记录；完成事件收到后先保存事实，再异步生成感想。正常离开、关页、断线不是唯一的保存触发点。
- 重连读取完成凭证并补写本机记录。已经完成的本机摘要不因事件补发重新花一次模型费用。
- 模型摘要失败时仍展示事实摘要，允许手动重试；模型不能改写事实中的完成状态和参与者。
- 私人经历只给本人角色的召回逻辑使用；分享游记是之后的独立动作。服务器保存的活动事实也受场次权限限制，“共同事实”不等于全站公开。
- 旧 `Memory` 数据保留，按旧小镇来源标记迁移；导入有格式、体积、字段与身份检查，存储不足必须提示并支持导出，不能静默宣称保存成功。
- 首版继续本机有界存储，不做云端人设同步。用户可以查看、删除和导出经历；删除后不再召回，避免重连时自动补回已明确删除的同一条经历。
